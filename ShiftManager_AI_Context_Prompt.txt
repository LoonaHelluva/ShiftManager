## Текущие ограничения и следующий приоритет

Главная оставшаяся проблема связей: Task ↔ StaffMember всё ещё моделируется через один nullable shadow FK `StaffMembers.HeliTaskId`. Поэтому один сотрудник не может корректно быть исполнителем нескольких Task: последняя задача перезаписывает FK. Для правильной модели нужна many-to-many join table, например `HeliTaskStaffMember`.

Другие задачи после этого:

4. Проверить DELETE-сценарии для связанных сущностей и отсутствие записей.
5. Добавить автоматические integration tests для связей и проверок зависимостей.

## Связи

Задуманные связи:

- Shift ↔ Helicopter — many-to-many через таблицу `HelicopterShift`.
- Shift → HeliTask — one-to-many через `ShiftId`.
- Helicopter → HeliTask — one-to-many.
- HeliTask → SubTask — one-to-many.
- Shift → StaffMember — связь сотрудников со сменой.
- HeliTask → StaffMember — исполнители задачи.
- SubTask → StaffMember — исполнители подзадачи.
- Shift.ManagerId должен ссылаться на StaffMember.

## Важная проблема EF-модели

Текущая миграция была создана с shadow foreign keys:

- в Tasks есть `HelicopterId`, хотя в сущности есть `HeliId`;
- в SubTasks есть `HeliTaskId`, хотя в сущности есть `TaskId`;
- в StaffMembers есть nullable `HeliTaskId`, `ShiftId`, `SubTaskId`;
- `Shift.ManagerId` в текущей миграции не оформлен как FK на StaffMembers.

Из-за этого нельзя автоматически предполагать, что `HeliId` и `TaskId` реально используются EF как внешние ключи.

Перед исправлением связей обязательно проверь:

- `Data/ShiftDbContext.cs`;
- текущую миграцию;
- `Migrations/ShiftDbContextModelSnapshot.cs`;
- entity-классы;
- фактические SQL-запросы EF при запуске.

Желаемое направление на будущее:

1. Явно настроить связи в `OnModelCreating`.
2. Выбрать единые имена FK.
3. Убрать неоднозначность между `HeliId`/`HelicopterId` и `TaskId`/`HeliTaskId`.
4. Добавить FK для `Shift.ManagerId`.
5. Создать новую корректную миграцию только после согласования модели.

Не меняй структуру связей молча: сначала объясни, какие FK сейчас реально существуют и что изменится.

Основное объяснение по `Include`:

```csharp
var helicopter = await _db.Helicopters
    .Include(h => h.Tasks)
    .Include(h => h.Shifts)
    .FirstOrDefaultAsync(h => h.Id == id);
```

Для вложенных данных:

```csharp
var task = await _db.Tasks
    .Include(t => t.SubTasks)
        .ThenInclude(st => st.Executors)
    .Include(t => t.Executors)
    .FirstOrDefaultAsync(t => t.Id == id);
```

`List<T>.Add()` — синхронный метод, поэтому правильно:

```csharp
collection.Add(entity);
await db.SaveChangesAsync();
```

Неправильно:

```csharp
await collection.Add(entity);
```

## Известные проблемы проекта

Учитывай следующие риски:

- `HeliId` не совпадает с фактическим shadow FK `HelicopterId`.
- `TaskId` не совпадает с фактическим shadow FK `HeliTaskId`.
- `ManagerId` пока не гарантирует существование сотрудника.
- `TaskDbService.AddTaskAsync` пока не проверяет существование Shift, Helicopter и Executors.
- `ShiftDbService.AddShiftAsync` пока не проверяет Manager.
- Task DTO принимает полноценные `StaffMember`, а не список Id.
- Task Service возвращает entity напрямую, что может привести к циклической JSON-сериализации.
- `GetHeliWithListsByIdAsync` нужно проверять на корректное включение всех навигаций.
- Часть навигаций объявлена полями вместо свойств.
- Некоторые endpoint-фильтры используют неправильные проверки строк:

```csharp
value == string.Empty && value == " "
```

Такая проверка не может одновременно быть истинной. Обычно нужна проверка через:

```csharp
string.IsNullOrWhiteSpace(value)
```

- Некоторые DELETE-методы не проверяют, существовала ли удаляемая запись.
- `ShiftDbService.DeleteShiftById` подавляет исключения через пустой `catch`.
- Обработка HTTP-ошибок пока неоднородна.
- Автоматических тестов нет.
- В проекте встречаются опечатки в именах, но сейчас приоритет — работающий MVP, а не косметический рефакторинг.
